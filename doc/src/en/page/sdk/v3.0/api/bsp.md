# BSP Board Support

The BSP (board support package) wraps the console UART, LED, button, and display resources on a specific board into board-independent interfaces; it is the module an application initializes first.

- Headers: `ecos/bsp/console.h`, `led.h`, `button.h`, `display.h`
- Board resources: `ecos/board_resources.h` (generated by the CLI into the project's `.ecos/generated/include/` based on the board manifest)
- Examples: `examples/get_start/hello`, `examples/get_start/blink`, `examples/peripherals/button/state`

## Console

The console is a CRLF text output channel plus a blocking text input channel; CR in the input is normalized to LF.

```c
ecos_err_t bsp_console_init(void);
int bsp_console_write(const char *text, size_t size);
int bsp_console_read(void *data, size_t size);
int bsp_console_try_read(uint8_t *data);
```

| Function | Description |
| --- | --- |
| `bsp_console_init()` | Initialize the console selected by the board; returns 0 or a negative error code. It is the first line of almost every application |
| `bsp_console_write()` | Output a piece of text (following the CRLF convention); returns the number of bytes consumed, or a negative error code on failure |
| `bsp_console_read()` | Blocking read until `size` bytes have been read; carriage return (CR) is normalized to line feed (LF) |
| `bsp_console_try_read()` | Non-blocking read of one byte: returns 1 if a byte was read, 0 if no data is currently available, or a negative error code on failure |

Logs are written to the console by default, so `bsp_console_init()` should be called first.

## LED

```c
typedef enum {
    BSP_LED_0 = 0,
    BSP_LED_1,
    BSP_LED_COUNT
} bsp_led_t;

typedef enum {
    BSP_LED_OFF = 0,
    BSP_LED_ON
} bsp_led_state_t;

ecos_err_t bsp_led_init(void);
ecos_err_t bsp_led_set_state(bsp_led_t led, bsp_led_state_t state);
```

| Function | Description |
| --- | --- |
| `bsp_led_init()` | Configure all on-board LEDs as GPIO outputs and set them to off |
| `bsp_led_set_state()` | Turn the specified LED on (`BSP_LED_ON`) or off (`BSP_LED_OFF`) |

`BSP_LED_COUNT` is the upper bound of the maximum number allowed by the public interface; the actual count is determined by the board.

## Button

```c
typedef enum {
    BSP_BUTTON_0 = 0,
    BSP_BUTTON_1,
    BSP_BUTTON_COUNT
} bsp_button_t;

typedef enum {
    BSP_BUTTON_RELEASED = 0,
    BSP_BUTTON_PRESSED
} bsp_button_state_t;

ecos_err_t bsp_button_init(void);
int bsp_button_get_count(void);
int bsp_button_get_state(bsp_button_t button);
```

| Function | Description |
| --- | --- |
| `bsp_button_init()` | Configure all on-board buttons as GPIO inputs |
| `bsp_button_get_count()` | Return the number of on-board buttons on the current board |
| `bsp_button_get_state()` | Return `BSP_BUTTON_RELEASED` (0) or `BSP_BUTTON_PRESSED` (1), or a negative error code on failure |

The button driver provides no debouncing and no interrupts; when debouncing is needed, implement it by polling in the application.

## BSP Display

When using the `bsp-display-st7735` component, the application can drive the on-board screen through a unified interface without handling QSPI configuration and the D/C, RST, and BLK pins itself:

```c
#include "ecos/bsp/display.h"

ecos_err_t bsp_display_init(void);
ecos_err_t bsp_display_deinit(void);
ecos_err_t bsp_display_fill_rect(uint16_t x, uint16_t y,
                                 uint16_t width, uint16_t height,
                                 uint16_t rgb565);
uint16_t bsp_display_width(void);
uint16_t bsp_display_height(void);
```

| Function | Description |
| --- | --- |
| `bsp_display_init()` | Initialize the display controller and panel according to the board manifest |
| `bsp_display_deinit()` | Turn the display off |
| `bsp_display_fill_rect()` | Fill a rectangle with an RGB565 color; errors such as not initialized or out of bounds are returned as `ecos_err_t` |
| `bsp_display_width()` / `bsp_display_height()` | Return the panel pixel dimensions |

The `display-donut` example demonstrates the complete BSP/Device/QSPI chain through this set of interfaces; for scenarios that directly use the ST7735/ST7789 device drivers, see [Device Drivers](device.md).

## Board Resources board_resources.h {#board-resources}

`ecos/board_resources.h` is generated by the `ecos` CLI when configuring the project, based on the resource manifest of the selected board, and does not exist in the SDK source tree. Each resource group uses `ECOS_BOARD_HAS_*` as an existence switch; example code uses `#if !ECOS_BOARD_HAS_*` + `#error` for compile-time assertions.

### GPIO Demo Resources

A set of input pins plus a set of output pins, which can be looped back and connected to each other:

```c
#define ECOS_BOARD_HAS_GPIO_DEMO 1
#define ECOS_BOARD_GPIO_DEMO_INPUT  { ECOS_GPIO_PORT_1, 7u }
#define ECOS_BOARD_GPIO_DEMO_INPUT_LABEL "GPIO1[7]"
#define ECOS_BOARD_GPIO_DEMO_INPUT_IDLE_LEVEL ECOS_GPIO_LEVEL_HIGH
#define ECOS_BOARD_GPIO_DEMO_OUTPUT { ECOS_GPIO_PORT_1, 5u }
#define ECOS_BOARD_GPIO_DEMO_OUTPUT_LABEL "GPIO1[5]"
#define ECOS_BOARD_GPIO_DEMO_OUTPUT_INITIAL_LEVEL ECOS_GPIO_LEVEL_HIGH
```

### QSPI Bus Resources

```c
#define ECOS_BOARD_HAS_QSPI_BUS 1
#define ECOS_BOARD_QSPI_BUS_CONTROLLER ((ecos_qspi_id_t)0u)
#define ECOS_BOARD_QSPI_BUS_CLOCK_DIVIDER 3u
```

### Software SPI Resources

```c
#define ECOS_BOARD_HAS_SOFT_SPI_BUS 1
#define ECOS_BOARD_SOFT_SPI_CHIP_SELECT { ECOS_GPIO_PORT_0, 0u }
#define ECOS_BOARD_SOFT_SPI_CLOCK       { ECOS_GPIO_PORT_0, 1u }
#define ECOS_BOARD_SOFT_SPI_MOSI        { ECOS_GPIO_PORT_0, 2u }
#define ECOS_BOARD_SOFT_SPI_MISO        { ECOS_GPIO_PORT_0, 3u }
#define ECOS_BOARD_SOFT_SPI_MODE        0u
```

The four pins and mode of `soft-spi-bus` come from the board manifest; the application fills these macros into `ecos_soft_spi_config_t` and must not rewrite the board GPIO numbers. See the [soft-spi component](components/soft-spi.md) for details.

### Display Resources

These are used field by field with the config structure of the ST7735/ST7789 device driver:

```c
#define ECOS_BOARD_HAS_DISPLAY 1
#define ECOS_BOARD_DISPLAY_CHIP_SELECT ECOS_QSPI_CS_0
#define ECOS_BOARD_DISPLAY_DC_PORT ECOS_GPIO_PORT_0
#define ECOS_BOARD_DISPLAY_DC_PIN 29u
#define ECOS_BOARD_DISPLAY_RESET_PORT ECOS_GPIO_PORT_0
#define ECOS_BOARD_DISPLAY_RESET_PIN 30u
#define ECOS_BOARD_DISPLAY_BACKLIGHT_PORT ECOS_GPIO_PORT_0
#define ECOS_BOARD_DISPLAY_BACKLIGHT_PIN 31u
#define ECOS_BOARD_DISPLAY_WIDTH 128u
#define ECOS_BOARD_DISPLAY_HEIGHT 128u
#define ECOS_BOARD_DISPLAY_ROTATION 0u
#define ECOS_BOARD_DISPLAY_HORIZONTAL_OFFSET 2u
#define ECOS_BOARD_DISPLAY_VERTICAL_OFFSET 3u
```

`display` corresponds to ST7735, and `display-st7789` corresponds to ST7789; the generator emits the same set of `ECOS_BOARD_DISPLAY_*` macros for both. Fixed wiring, or an RST or BLK that has no software control, may be omitted from the board manifest; the corresponding `*_PORT` macro is then `ECOS_GPIO_PORT_COUNT`, and the device driver will not access that pin.

## Minimal Skeleton

```c
#include "ecos/bsp/console.h"
#include "ecos/bsp/led.h"
#include "ecos/driver/timer.h"
#include "ecos/log.h"

#define LOG_TAG "blink"

int main(void)
{
    ECOS_PANIC_ON_ERROR(LOG_TAG, bsp_console_init(), "initialize console");
    ECOS_PANIC_ON_ERROR(LOG_TAG, bsp_led_init(), "initialize LED");

    for (;;) {
        ECOS_PANIC_ON_ERROR(LOG_TAG,
                            bsp_led_set_state(BSP_LED_0, BSP_LED_ON), "LED on");
        ECOS_PANIC_ON_ERROR(LOG_TAG,
                            ecos_timer_delay_ms(ECOS_TIMER_DEFAULT, 500u),
                            "delay");
        ECOS_PANIC_ON_ERROR(LOG_TAG,
                            bsp_led_set_state(BSP_LED_0, BSP_LED_OFF), "LED off");
        ECOS_PANIC_ON_ERROR(LOG_TAG,
                            ecos_timer_delay_ms(ECOS_TIMER_DEFAULT, 500u),
                            "delay");
    }
}
```

## Notes

- `bsp_console_init()` should be called first: logs are written to the console by default, and even when initialization fails, `ECOS_PANIC_ON_ERROR` can output error information.
- The console writes text: `\n` is prefixed with `\r` to form CRLF; for a binary channel, use the [UART driver](driver/uart.md).
- The specific values of `board_resources.h` vary by board; when porting code across boards, rely only on the macro names and do not hard-code pins.
- The actual number of LEDs/buttons is determined by the board; numbers outside `BSP_LED_COUNT` / `BSP_BUTTON_COUNT` have undefined behavior.
- For the correspondence between on-board resource logical pins and the Demo examples, see [Example Projects](../examples.md).
