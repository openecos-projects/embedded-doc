### Board Introduction
The StarrySky development board v1.3 uses a design consisting of an SoC base board plus an FPGA SoM. The FPGA SoM uses the ZYNQ7010 chip. The onboard resources of the SoC base board are shown below:

![](../../../res/img/brd/starry-sky-l/v1.3/core/board_func_color.webp)
/// caption
SoC base board onboard resources
///

As can be seen in the figure above, most of the SoC peripherals and interfaces are located on the lower-middle part of the board **(purple)**, while the PL and PS peripherals of the FPGA part are mainly located on the upper part and both sides of the board **(green and blue)**. Detailed descriptions of the peripherals and interfaces are provided in the table below:

- SoC
    - 1 active crystal oscillator socket
    - 1 TF card socket in SPI mode
    - 1 onboard programmer (HFPLink)
    - 1 Flash socket with a built-in NOR Flash chip; after the SoC resets, it fetches instructions from this Flash chip
    - 1 UART interface, using the CP2102 chip
    - 1 external 5 V DC power input, using a Type-C connector
    - 2 power mode selector switches
    - 1 latching power switch
    - 2 DIP switches for setting the PLL clock output and core selection
- System
    - 1 red power indicator LED
    - 1 PS function reset button, 1 PS debug reset button
    - 1 FPGA boot mode selector switch
    - 1 FPGA JTAG debug interface
    - 1 FPGA peripheral function selector switch
- PS-side peripherals
    - 1 UART interface, using the CP2102 chip
    - 1 SDIO interface; the SD card can boot PetaLinux, and the eMMC can store programs
    - 1 SDIO WiFi module, using the AP6212 module, with independent power control
    - 1 CAN interface, using the TJA1050 high-speed transceiver chip
    - 1 USB HOST, using the USB3320C chip
    - 1 6-pin PMOD expansion port
    - 2 user-defined buttons
    - 2 user-defined blue LEDs
    - 4 WS2812C RGB LEDs
- PL-side peripherals
    - 1 VGA interface, using a resistor network to implement the DAC
    - 1 PS/2 interface for connecting a PS/2-compatible keyboard
    - 1 RTC clock, using the PCF8563 chip
    - 1 EEPROM, using the AT24C64 chip
    - 1 SPI Flash, using the W25Q128JVSIQ chip
    - 1 I2S interface, using the WM8960 chip; supports audio input/output and MIC recording
    - 1 user-defined button
    - 1 user-defined blue LED
    - 1 general-purpose IO, often used to output a clock for frequency adjustment
    - 4 WS2812C RGB LEDs
- 1 SO-DIMM 204P connector for connecting the ZYNQ7010/7020 FPGA SoM

The FPGA SoM onboard resources are as follows:

- Main chip: XC7Z010CLG400
- DDR3: MT41K128M16JT-125 x2 **(512 MB)**
- eMMC: KLM8G1GETF-B041 **(8 GB)**
- Flash: W25Q128JVSQ **(16 MB)**

The main design features of the StarrySky v1.3 board are as follows:

- The StarrySky development board measures **110 x 84 mm**, about **twice** the area of a standard credit card.
- The power network was redesigned, increasing the power delivery capability from 1.2 A to 2 A. It supports power from an external **5 V power adapter** and supports multiple power rails.
- The FPGA uses an SoM design with a SO-DIMM 204P connector; hardware specifications: **XC7Z010-1CLG400C + 512 MB DDR3 + 8 GB eMMC**.
- An onboard NOR Flash programmer **(HFPLink)** provides drag-and-drop programming; the programmer supports firmware upgrades **(via an ISP that supports the USB protocol)**.
- Multiple **analog switches** are used to **multiplex the PL-side IO** so that as many peripherals as possible can be attached, while all IOs on the FPGA SoM are broken out.
- The processor core switching and frequency selection switches are separated in the design and use **active-high selection logic**, making DIP switch operation convenient.
- Geometric constraints were fully considered, and low-actuation-force switches **(160 gf)** were selected to improve the hardware operating experience.
- **Silkscreen labels and markings are provided for DIP switches and important interfaces on the board** for ease of use.

The hardware resource block diagram for the StarrySky v1.3 board is shown below:

![](../../../res/img/brd/starry-sky-l/v1.3/core/board_res.webp)

Hardware resources

The PS-side banks of the FPGA SoM are BANK502, BANK500, and BANK501. BANK502 uses a 1.5 V level standard and connects to two DDR3 chips. BANK500 uses a 3.3 V level standard and connects to peripherals that comply with the 3.3 V electrical standard, such as UART, LEDs, and buttons. BANK501 uses a 1.8 V level standard and connects to peripherals that comply with the 1.8 V electrical standard, such as USB HOST and I2S.

!!! danger "Power Supply Load"
    - At present, the current load of the StarrySky development board during normal program operation is about **400~450 mA**. Power from a standard USB port on a laptop or desktop computer is generally sufficient, and **no additional power supply is required**. Of course, to meet certain specific requirements, the StarrySky development board also supports power from an external 5 V/2 A power adapter via the Type-C connector. However, the project team does not include such an adapter in the accessories, so students who need one must prepare it themselves.
    - Power adapters are generally connected directly to the mains and involve relatively high voltages and currents, so they carry some risk. **If you do need to use a power adapter to power the board, please choose an adapter that meets safety standards and pay attention to electrical safety**.

This section mainly describes how to perform basic hardware and software tests on the board. To make testing convenient, **the Flash socket on the board already contains a NOR Flash chip programmed with an RT-Thread program**. In addition, before the board was shipped, the project team ran this test on all cores in the SoC. Students only need to follow the sequence of operations described below to run the RT-Thread program. The specific power-on test steps are shown below, divided mainly into **hardware operations** and **software setup**:

![](../../../res/img/brd/starry-sky-l/v1.3/core/test_flow.webp)
/// caption
Power-on test steps
///

The yellow boxes indicate purely hardware operations, while the blue boxes involve software operations.

!!! warning "Debugging Notes"
    Please read carefully and confirm each of the following notes before actually operating the board. This is especially important for students without prior embedded debugging experience; please be sure to follow these notes:

    - Before touching the board or other materials, confirm that your hands are dry.
    - Before touching the board, first touch a metal object to discharge any static electricity that may have built up on your body.
    - When handling the board, hold it by the edges of the circuit board so that you avoid touching the chips as much as possible, preventing excess static electricity from your body from reaching the chip pins.
    - When powering the board with a Type-C cable, prefer a USB 3.0 port on the PC to ensure the most stable power supply possible.
    - The board has power selector switches, slide switches, and DIP switches. Before powering on, confirm that each is correctly moved to one side rather than the middle position **(dead zone)**. In addition, try to ensure that no switch is moved while the board is powered.
    - Do not connect the SoC board and FPGA SoM while powered, to prevent latch-up caused by improper hot-plugging and damage to the chips.
    - Once power is applied, if you observe smoke, unusual odor, arcing sounds or flashes, hot components, or other abnormalities—especially a **high-pitched buzzing noise**—immediately **disconnect the power**.

!!! info "Acoustic Noise"
    Acoustic noise is commonly divided into inductor whine and capacitor whine. Inductor whine is the most common and is often caused by improperly selected component parameters, unstable load, light load, or overload. **Unstable load** is often the main cause, which means there may be a short circuit somewhere on the board.

#### Hardware Operations

First, students need to take the board out of the **mesh anti-static bag**. At present, the One Student One Chip (YSYX) SoC **accesses the DDR3 chips on the FPGA side through the ChipLink interface to implement the memory access path**, so an FPGA SoM is required for RT-Thread to boot correctly:

![](../../../res/img/brd/starry-sky-l/v1.3/core/datapath.webp)
/// caption
Three data paths supported by the YSYX SoC
///

In fact, the FPGA SoM is already inserted into the back of the board in advance, **so students do not need to install it themselves**. In addition, a crystal oscillator must be inserted into the SoC board for it to work correctly; **this crystal oscillator has also already been inserted into the oscillator socket on the board**, so students only need to check it.

!!! info "Installing/Removing the FPGA SoM and Crystal Oscillator"
    The FPGA SoM supplied with this SoC is a [SoM (System on Module)](https://en.wikipedia.org/wiki/System_on_module) using a SODIMM 204P connector design **(DDR3-standard-compatible connector)**. This type of connector is commonly used for laptop memory modules. The FPGA SoM is inserted into the socket by default and **generally does not need to be removed**. If removal is truly necessary, students must do it themselves. The specific method is as follows:

    ![](../../../res/img/brd/starry-sky-l/v1.3/fpga/sodimm_black_1.webp)
    /// caption
    Installing the FPGA SoM
    ///

    To install the FPGA SoM, insert it into the socket at **an angle of about 30 degrees**, **making sure that all gold fingers are inserted to the same depth**, then grasp both sides of the FPGA SoM with both hands and press down simultaneously until both sides are under the socket's **retaining clips** and a "click" is heard. To remove the SoM, reverse the process: gently push the retaining clips outward, the FPGA SoM will pop up automatically, and then pull it out.

    Installing and removing the crystal oscillator is easier than installing and removing the FPGA SoM. Simply take a 25 MHz crystal oscillator out of the **rigid anti-static bag** and insert it into the board's oscillator socket in the correct orientation. Because the oscillator pins are longer than the depth of the socket slots, **there is no need to insert it all the way**. When you find that gentle force can no longer push it in any further, stop. The correct orientation and depth are shown below:

    ![](../../../res/img/brd/starry-sky-l/v1.3/perip/osc_1_1.webp)
    /// caption
    Correct crystal oscillator orientation
    ///

    ![](../../../res/img/brd/starry-sky-l/v1.3/perip/osc_2.webp)
    /// caption
    Correct crystal oscillator insertion depth
    ///

!!! warning "Note"
    - Do not insert the crystal oscillator in the wrong orientation; **students must confirm this again before powering on**.
    - You can remove and insert the crystal oscillator directly by hand, but try not to touch its pins.
    - You can hold the metal case of the crystal oscillator when inserting or removing it.

After the crystal oscillator is correctly inserted, the SoC chip's operating state must also be set correctly using the **micro DIP switches**. Specifically, two steps are required:

- Enable the PLL output and select the PLL output core clock frequency.
- Select the processor core for a specific student ID.

During back-end integration of the Phase 3 SoC, the project team assigned an index to each student's core, and that index can be used to select your own core. First, open the [Phase 3 processor core index and student ID mapping table (student-id.md)](https://github.com/maksyuki/StarrySky-res/blob/main/software/v1p3/student-id.md), **then look up your core index according to your student ID**. For example, the core with student ID `ysyx_210324` has core index `22`.

Now let us explain the function of each position on the **micro DIP switches**. There are two micro DIP switches on the board. The left one has 4 positions and is used to **set the clock output state**. The right one has 6 positions and is used to **set the core selection state**:

![](../../../res/img/brd/starry-sky-l/v1.3/perip/dip_switch_1.webp)
/// caption
DIP switch position function definitions
///

Functions of the 4-position DIP switch **(from left to right)**:

- PLL clock enable bit **(1 bit)**
- PLL output clock frequency selection bits **(3 bits)**

Functions of the 6-position DIP switch **(from left to right)**:

- Undefined **(1 bit)**
- Processor core selection bits **(5 bits)**

!!! warning "Core Selection DIP Switch Definition"
    The highest bit of the 6-position DIP switch **(the first position from the left)** has no defined function.

DIP switch setup has two parts. The first is setting the PLL clock enable bit and the PLL output core clock frequency. We recommend **first setting the PLL output core clock frequency to 25 MHz and starting testing at a low frequency**. Once your core can run the provided test programs at a 25 MHz core clock, you can try gradually increasing the processor core clock frequency. The relationship between the DIP switch positions and the signals in the SoC is described below. The RCG **(global clock and reset module)** of the Phase 3 SoC is shown below:

![](../../../res/img/brd/starry-sky-l/v1.3/core/rcg_intro.webp)
/// caption
RCG module of the Phase 3 SoC
///

The **PLL clock enable bit** on the DIP switch corresponds to `clk_sel` in the red box in the upper-left corner of the figure above. When `clk_sel=1`, the processor core clock `clk_core` uses the PLL output clock; in this case, set the **PLL clock enable bit** on the DIP switch to `ON`. When `clk_sel=0`, `clk_core` directly uses the external active crystal oscillator clock `sys_clk`; in this case, set the **PLL clock enable bit** on the DIP switch to `OFF`.

In addition, the **PLL output clock frequency selection bits** correspond to `pll_cfg[2:0]` in the red box in the upper-left corner of the figure above, and are used to set the PLL output clock frequency, that is, the processor core clock frequency. The **relationship between the DIP switch positions and the PLL output core clock frequency** is shown in the table below:

| PLL output clock frequency selection bits (0 = OFF position, 1 = ON position) | Processor core clock frequency |
| :-: | :-: |
| 3'b000 | 25 MHz  |
| 3'b001 | 50 MHz  |
| 3'b010 | 100 MHz |
| 3'b011 | 150 MHz |
| 3'b100 | 200 MHz |
| 3'b101 | 250 MHz |
| 3'b110 | 300 MHz |
| 3'b111 | 350 MHz |

For example, when the PLL output bits are set to `OFF-OFF-OFF`, the PLL output core clock frequency is 25 MHz. In fact, the clock setting in the figure titled ***DIP Switch Position Function Definitions*** is exactly 25 MHz.

!!! tip "Clock DIP Switch Settings"
    The lowest bit of the **PLL output clock frequency selection bits** in the table ***DIP Switch Position and Core Clock Frequency Mapping*** corresponds to position 4 of the DIP switch on the board. Therefore, to set the PLL output clock frequency to 200 MHz, set the PLL output clock selection bits to `ON-OFF-OFF` **(corresponding to DIP switch positions 2-3-4)**, as shown below:

    ![](../../../res/img/brd/starry-sky-l/v1.3/perip/dip_switch_2.webp)
    /// caption
    DIP switch settings for enabling the PLL and multiplying the clock to 200 MHz
    ///

!!! tip "Tips"
    - If the DIP switch has **a yellow dust-protective film** on it, peel it off before moving the switches.
    - The mechanical DIP switches on the board use a 1.27 mm pitch micro DIP switch. Each position is small and difficult to move directly by hand. You can use tweezers, a paper clip, or another pointed object. **Please use pointed objects safely**.
    - To make it easier to measure the processor core clock frequency, the board provides **a core clock divide-by-4 test point** and **an external crystal oscillator clock test point**:

    ![](../../../res/img/brd/starry-sky-l/v1.3/perip/osc_tp.webp)
    /// caption
    Clock frequency test points
    ///

    The **external crystal oscillator clock test point** is used to check whether the external active crystal oscillator starts correctly, while the **core clock divide-by-4 test point** is used to measure the core clock frequency. Students with an oscilloscope can use this test point to measure the PLL core clock output at different DIP switch settings. **Note, however, that the measured value is one quarter of the PLL core clock**.

The second part of DIP switch setup is selecting your own processor core. YSYX Phase 3 integrates multiple students' cores into one SoC and uses the logic level of external signal lines to select different cores. These external signal lines are provided by the **processor core selection bits** on the DIP switch, which correspond to `core_dip[4:0]` in the red box on the left side of the Phase 3 SoC architecture diagram below:

![](../../../res/img/brd/starry-sky-l/v1.3/core/soc_intro.webp)
/// caption
Phase 3 SoC architecture diagram
///

The processor core selection switches also use **positive logic**, which is easier to understand with the example below. For example, to select core index 3, set the DIP switch positions as shown below:

![](../../../res/img/brd/starry-sky-l/v1.3/perip/dip_switch_3.webp)
/// caption
DIP switch position and index mapping
///

From left to right, the **bit weights** of the five core selection switch positions are `16, 8, 4, 2, 1`. Thus, to select core index `1`, the corresponding code is `5'b00001`. Because the logic is **positive**, the DIP switch positions from left to right are `OFF-OFF-OFF-OFF-ON`. To select core index `6`, the code is `5'b00110`, so the DIP switch positions from left to right are `OFF-OFF-ON-ON-OFF`.

!!! danger "Changing DIP Switches"
    - Like slide switches, DIP switches must be correctly moved to one side rather than the middle position **(mechanical dead zone)** before powering on, to prevent the SoC from sampling an unstable DIP switch level.
    - Do not move DIP switches while the board is powered. Doing so may cause large surge currents in the board's power network, affecting the board's operating stability or even damaging the board.

### Hardware Design
This section describes the hardware design of the StarrySky v1.3 board in detail. First, a brief summary of the main hardware design features of the v1.3 board:

- Designed with Cadence Orcad/Allegro **(three weeks)**, using a **six-layer** stackup **(TOP-GND02-ART03-PWR04-GND05-BOT)** and an ENIG surface finish, and passing four-wire low-resistance testing.
- Board length matching: ChipLink traces are matched within each group to **0/50 mil** with respect to **tx_clk** and **rx_clk** respectively; the two SDIO signals are matched within the group to **0/30 mil** with respect to clk; USB 2.0 is matched within the group to **0/50 mil** with respect to clk; and the five USB differential pairs are matched within each pair to **0/25 mil**.
- Ground vias are placed at **30 mil** spacing on both sides of the SDIO WiFi IPEX antenna, and **cutouts** are made between the pads of the power inductor.
- The VGA and all crystal oscillator clock outputs are **surrounded by ground**, kept away from high-speed and analog signals, and all reference a solid ground plane.
- Analog ground uses **single-point isolation**; every chip has complete power filtering; the power network is connected with copper pours to ensure stable power delivery, with sufficient **return ground vias**.

#### Power Network
The power network topology of the SoC board is shown below:

![](../../../res/img/brd/starry-sky-l/v1.3/core/power_tp.webp)
/// caption
Board power network topology
///

As can be seen in the figure above, the entire board uses a single 5 V supply. To control peripheral power flexibly, the board provides three power inputs:

- 5 V from the SoC USB serial port
- 5 V from the FPGA PS-side USB serial port
- 5 V DC power adapter input via the external USB connector

The board uses a **power selector switch** to select one of these three inputs to supply the board. After passing through the **latching power switch**, the 5 V supply is stepped down by three LDO chips to 3.3 V, 1.8 V, and 1.2 V for the SoC and FPGA peripherals. The schematic is as follows:

![](../../../res/img/brd/starry-sky-l/v1.3/sch/sch_pwr_sck.webp)
/// caption
Power input connectors
///

USB_PWR, PS_PWR, and DC_PWR are three standard Type-C receptacles. USB_PWR exposes the power net **`5V_VBUS1`** and the differential input signals **`MAIN_DP/DN`** required by the SoC serial port. PS_PWR exposes the power net **`5V_VBUS2`** and the differential input signals **`PS_UART_DP/DN`** required by the FPGA PS-side serial port. Because DC_PWR is used only for power, it exposes only the power net **`5V_DC`**.

!!! info "Purpose of the 5.1K Pulldown Resistors on the CC Pins of the Type-C Receptacle"
    The CC pins on a Type-C connector are collectively called the [Configuration Channel](https://en.wikipedia.org/wiki/USB-C). They are used to detect cable insertion, identify cable orientation, configure the operating mode **(current, PD mode)**, and negotiate DFP **(downstream-facing port, host side)** and UFP **(upstream-facing port, device side)** roles. Relative to the PC host, the board's Type-C port acts as a device port, that is, it has a UFP role. The specification requires a pulldown resistor **`Rd=5.1KΩ`** on both the **`CC1`** and **`CC2`** pins of a UFP.

The three power inputs described above pass through two [single-pole double-throw (SPDT) slide switches](https://en.wikipedia.org/wiki/Switch#Contact_terminology), PWR-SEL1 and PWR-SEL2. By combining the positions of these two switches, one supply is selected for the **PWR-LOCK latching power switch**. PWR-LOCK is a [double-pole double-throw (DPDT) slide switch](https://en.wikipedia.org/wiki/Switch#Contact_terminology), and only one side of the switch is used here. When the latching switch is not locked down, it connects pins **`2`** and **`1`**, and the power net is not connected. When the latching power switch is pressed down and locked, PWR-LOCK connects pins **`2`** and **`3`**, allowing one supply to pass through the latching switch into the downstream power network. The supply then passes through two protection devices—the bidirectional TVS diode SMAJ5.0CA and a 2 A fuse—and is filtered by multiple capacitors, ultimately producing a stable 5 V digital supply **`5V_IN`**:

![](../../../res/img/brd/starry-sky-l/v1.3/sch/sch_pwr_sel.webp)
/// caption
Power selector switch
///

The **`5V_IN`** rail then enters three RT2515H LDO chips and is stepped down to 3.3 V, 1.8 V, and 1.2 V. The RT2515H is a high-performance voltage regulator that supports a dropout voltage as low as 200 mV and a maximum output current of 2 A. Configuring the resistor values on its **`ADJ`** pin produces different output voltages. In addition, the 3.3 V power net **`VCC_3V3`** is connected to a red LED to indicate whether the power circuit is working properly:

![](../../../res/img/brd/starry-sky-l/v1.3/sch/sch_pwr_ldo.webp)
/// caption
Power conversion circuit
///

#### SoC Onboard Programmer (HFPLink) {#soc-hfplink}
The SoC section of the board includes a NOR Flash programmer called **HFPLink**. **HFPLink** was actually designed by the project team. **HFP** stands for **High-speed QSPI-Flash Programmer**, and because it supports drag-and-drop programming like **DAPLink**, the suffix **Link** was added following that naming convention, forming the name **HFPLink**. The HFPLink part of the schematic is essentially the CH32V103 minimal system plus an external NOR Flash **(SPI protocol)** and a USB interface. The core functionality is actually implemented in software.

#### SoC Function Switch {#soc_2}
The function switch in the SoC section is designed to let the SoC's USB-to-serial and HFPLink share one Type-C connector while switching the NOR Flash operating state at the same time. This function is controlled by a single-pole double-throw slide switch named HFP-SW. When HFP-SW is moved so that pins **`1`** and **`2`** are connected, the **`PROG_SW_SEL`** net is low. At this time, pin **`6`** of every WAS3157B analog switch is low, which connects the signal nets on pins **`1`** and **`4`** of each analog switch. When HFP-SW is moved so that pins **`3`** and **`2`** are connected, the **`PROG_SW_SEL`** net is high. At this time, pin **`6`** of every WAS3157B analog switch is high, which connects the signal nets on pins **`3`** and **`4`** of each analog switch:

![](../../../res/img/brd/starry-sky-l/v1.3/sch/sch_soc_func_sw.webp)
/// caption
SoC function switch
///

This circuit is possible because **HFPLink and the SoC USB-to-serial do not operate at the same time**, so the differential pair **`MAIN_DP/DN`** on one Type-C connector can be shared. Moreover, when HFPLink programs the NOR Flash, the SoC's SPI signal lines to the NOR Flash must be disconnected; conversely, when the SoC needs to fetch and execute code from the NOR Flash, HFPLink's SPI signal lines to the NOR Flash must also be disconnected. In other words, the connection states of six signal lines—two differential and four SPI—must be **switched together** between the two states of HFPLink operation and normal SoC operation.

!!! info "Calculating Resistor Network Values"
    The VGA standard specifies that the `VGA_R`, `VGA_G`, and `VGA_B` pins carry analog signals in the range `0~0.714V`. For each analog channel, a voltage of `0V` represents no color, and `0.714V` represents full color. Because RGB444 mode is used, each channel has 2^4=16 color levels. For the `VGA_R` channel, let the value of the combined input signals VGA_R3~VGA_R0 be $VGA_R[3:0]$, and let the voltage of the `VGA_R` net be $V_{R}$. To display the `VGA_R` channel correctly, the following conditions must be met:

    - When $VGA_R[3:0]=4'b0000$, $V_{R}=0V$
    - When $VGA_R[3:0]=4'b1111$, $V_{R}<=0.714V$
    - When $VGA_R[3:0]$ takes any value in $[4'b0000, 4'b1111]$, for any two values $VGA_R[3:0]_1 <= VGA_R[3:0]_2$, $V_{R1}<=V_{R2}$ holds

    It follows that the resistor weights for VGA_R3~VGA_R0 are different. The exact resistance values can be calculated with circuit simulation software, such as the free [MultisimLive](https://www.multisim.com/):

    ![](../../../res/img/brd/starry-sky-l/v1.3/sch/vga_dac_sim.webp)
    /// caption
    Simulating the VGA resistor network with MultisimLive
    ///

    The free version of **MultisimLive** has limits on circuit size, but it is entirely sufficient for the resistor network calculation task here.

At this point, all of the board's hardware design has been covered. The following sections describe the FPGA part.

!!! info "Why the Xilinx ZYNQ Series Was Chosen for the FPGA"
    - There are more Xilinx ZYNQ development boards on the market than boards based on other FPGA models, so more software and hardware reference material is available.
    - ZYNQ PS-side peripheral controllers can be routed to PL-side IOs through EMIO, making it convenient to compare and verify them against IP developed by the project team.
    - The FPGA SoM used on this version of the board not only provides the ChipLink memory access support required by the SoC, but also **provides board support for FPGA prototyping of the next-generation SoC**. Achieving this requires an FPGA device with efficient and stable software development tools and IP component support. The project team also evaluated several domestic FPGAs during device selection, but their software development environments still have much room for improvement compared with Xilinx's **Vivado + Vitis**, so the team ultimately chose Xilinx ZYNQ series FPGA devices.

#### ChipLink Hardware System

!!! info "ChipLink Pre-programming"
    Before the FPGA SoM is shipped to students, the ChipLink hardware system described in this section has already been programmed into the FPGA onboard Flash. Students can use it directly and do not need to compile and download it themselves.

ChipLink is a low-speed chip-to-chip bus communication protocol proposed by SiFive **(between the FPGA and the SoC)**. It is mainly used to fragment and reassemble AXI4 requests sent by the SoC so that hardware logic resources on the FPGA can be accessed reliably. The Verilog code for the ChipLink controller on this FPGA SoM was generated from Chisel and verified in VCS simulation. Specifically, `ChiplinkTop` and all its submodules used in VCS simulation were imported into a single file and renamed `ChiplinkTop.v`. Because many signals inside the `ChiplinkTop` instantiated during VCS simulation are dangling or tied to constants, the project team wrapped another layer called `chiplink_ctrl` around `ChiplinkTop`. This module instantiates `ChiplinkTop`, ties the appropriate ports to constants, and was named `chiplink_ctrl.v`. In addition, because the ZYNQ DDR address map differs from the SoC memory access address range, the memory access addresses must be remapped. The ZYNQ memory address map is shown below:

![](../../../res/img/brd/starry-sky-l/v1.3/fpga/chiplink_addr_map.webp)
/// caption
ZYNQ OCM/DDR address map
///

OCM stands for **On-Chip Memory**, which is built into the ZYNQ chip and can serve as low-latency shared memory between the two PS-side CPUs. OCM is also the memory in which the dual-core CPU executes applications, **so you must ensure that Phase 3 SoC memory access addresses are correctly mapped into DDR space; if they are remapped into OCM space, the program running on the PS side may be overwritten**. As can be seen in the figure above, ZYNQ supports a 1 GB address range from `0x0010_0000` to `0x3FFF_FFFF`, while the ZYNQ SoM provided to students has only 512 MB of onboard DDR3. To simplify the implementation, we **remap** Phase 3 SoC memory access requests starting at `0x8000_0000` to `0x0010_0000`. In this way, as long as the addresses accessed by the PS-side CPU when it needs to access DDR do not overlap with the SoC memory access addresses, the mapping works. The remapping code is as follows:

```verilog
assign io_axi4_0_awaddr = aw_addr - 32'h8000_0000 + 32'h0010_0000;
assign io_axi4_0_araddr = ar_addr - 32'h8000_0000 + 32'h0010_0000;
assign chiplink_cpu_int = 1'b0;
```

Adding `chiplink_ctrl` to the **Block Design** and connecting it to the ZYNQ system completes the hardware design. The final hardware system is shown below:

![](../../../res/img/brd/starry-sky-l/v1.3/fpga/chiplink_bd.webp)
/// caption
ChipLink hardware system Block Design
///

The **ZYNQ Processing System** enables the AXI HP slave interface, the `FCLK_CLK0` and `FCLK_CLK1` clock outputs, and the `FCLK_RESET0_N` reset output. `FCLK_CLK0` is set to 25 MHz and supplies the input clock for `chiplink_ctrl`. `FCLK_CLK1` is set to 100 MHz for AXI master communication by the **AXI Interconnect**. The two clocks also feed their respective **Processor System Reset** blocks to generate reset signals. Finally, an ILA core is added to sample the AXI4 signals of `chiplink_ctrl`.

After that, the pins of the `chiplink_ctrl` module must be constrained. Because `chiplink_ctrl` has many pins, they must be checked carefully. In addition, the Phase 3 SoC uses a 110 nm process, so the pin level standard must be constrained to LVCMOS33. Finally, clock constraints must be applied to the `chiplink_ctrl` pins, as shown below:

![](../../../res/img/brd/starry-sky-l/v1.3/fpga/chiplink_contr.webp)
/// caption
ChipLink timing constraints
///

Then synthesize and place-and-route with Vivado. After routing, Vivado reported three timing-related Critical Warnings. After consulting Xilinx's **UG906** manual and analyzing the design code, the project team believes that these three warnings are mainly because **the clock source generated by the PS-side MCM/PLL cannot have a common path defined on the PL side**, and that this does not affect the design, so the warnings can be ignored.

![](../../../res/img/brd/starry-sky-l/v1.3/fpga/chiplink_log.webp)
/// caption

///
